指南滑不动时先补一次小拖动（模拟"手动滑一下就好了"）

用户实测证据:
  同一台机器、同一坐标、同一 IPC 路径(settle_time=True)，三次结果:
    往下找 699->292(用户线)  5 次 平均 12.170  -> 生效
    往上找 360->630(内缩线)  5 次 平均 11.801  -> 生效
    往下找 630->360(内缩线)  5 次 平均  0.000  -> **全 0**
  同一个人的调试日志里，用户线和内缩线**都出现过全 0** —— 所以和坐标无关，
  确认是**偶发**。

而用户补充的那句是定性的关键:
  **滑不动出现后，自己手动滑一下，软件就能继续滑**
=> 卡住的是**注入的触摸状态**（多半是上一次手势的"抬起"没送达，
   游戏以为手指还按着，之后的拖动被当成同一次按住而不生效），
   不是坐标、也不是列表位置（后者会导致 at_guide_bottom() 触发，
   但实测没有触发）。

改动 guide_nav:
  * 新增 cleanup_stuck_touch(): 发一个**完整的小拖动**把卡住的触摸状态冲掉 ——
    相当于把用户手动那一下自动化
      - 起点 (0.5, 0.45) —— **不在左侧列表里**，避免把条目点开
      - 位移 30px —— **超过触摸阈值**，不会被当成"点击"
      - 用 gesture 不用 click；耗时约 0.3 秒
  * 接到 _sweep_entry 的"画面没动"分支，且排在两级补救**之前**:
      清状态 -> 慢速拖动 -> 内缩起止线 -> 计入 stuck_streak
    理由: 如果是触摸卡住，慢速拖动和内缩线都救不回来，而这一下很便宜。

门禁新增 TestGuideStuckTouchCleanup(3 个用例):
  * 起点必须在列表之外、位移要超过触摸阈值、耗时 <= 1 秒
  * 顺序必须是"清状态 -> 慢速 -> 计入失败"
  * 只能用 gesture，不许用 click（click 会误触发）
